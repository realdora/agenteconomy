# Dune restart runbook — 2026-06-29 (original account renewal)

Supersedes `RESUME-RUNBOOK.md` (incremental-fork era — keep for archaeology
only). All code is already written and offline-tested (`run-tests.mjs`); this
runbook is verification + wiring, no development.

**Ground rules:** original account only (NO new free accounts — ban evasion).
Human pace: max 1–2 executions per day during validation. The local
`~/.config/dune/agenteconomy.env` key is the SUSPENDED account's until step 1
replaces it.

## Step 0 — confirm renewal (6/29)
Log into dune.com (original account) → Settings → Subscription: credits reset
to 2,500. If not yet reset, stop and retry next day.

## Step 1 — local key (Dora)
Dora provides the ORIGINAL account's API key via the osascript dialog flow
(never paste in chat) → overwrite `~/.config/dune/agenteconomy.env`. The GitHub
secret `DUNE_API_KEY` is already this account's key — do not touch it.

## Step 2 — recreate the two queries (web UI, costs nothing)
Creating/saving a query is not an execution.
1. New query → paste `scripts/dune/x402-recent-window.sql` → add a **TEXT
   parameter `window_start`, default `2026-05-01`** → save as private. Note id.
2. New query → paste `scripts/dune/erc8004-registry-recent-window.sql` → same
   parameter → save. Note id.

## Step 3 — exact baselines (READ-only, no executions)
```
source ~/.config/dune/agenteconomy.env   # or however the key is exported
node scripts/dune/build-baseline.mjs
node scripts/test/run-tests.mjs          # must stay 60/60 green
git add scripts/dune/baselines.json && git commit
```
This replaces the approximate protocol split (derived from rounded display
shares) with exact per-facilitator numbers from a read of Q6058135's stored
result, and builds the registry baseline from Q6130922's stored result. It
aborts if either stored result predates the 2026-05-01 cutoff.

## Step 4 — first x402 window execution (day 1: ONE execution)
```
DATA_OUT_DIR=/tmp/dune-live DUNE_MAX_EXECUTIONS_PER_RUN=1 \
DUNE_QID_X402_CUMULATIVE=<x402-window-id> \
node scripts/fetch-data.js
```
Record: runtime (must be well under 120s), credits consumed (dashboard), and
reconcile `/tmp/dune-live/data.json` x402 totals vs the 06-05 build
(150,005,139 txs — new total must be ≥ that, May+Jun rows refreshed, frozen
months byte-identical).

## Step 5 — registry window execution (day 2: ONE execution)
Same as step 4 with `DUNE_QID_REGISTRY=<registry-window-id>` added. evms.logs
scans are the heavy ones — if this times out at 2 min, see §registry-fallback.

## Step 6 — wire CI + re-enable cron (day 3)
```
gh variable set DUNE_QID_X402_CUMULATIVE -b "<x402-window-id>" -R realdora/agenteconomy
gh variable set DUNE_QID_REGISTRY      -b "<registry-window-id>" -R realdora/agenteconomy
gh workflow enable "Update Dune Data" -R realdora/agenteconomy
```
(The workflow already reads these as repo variables; no code change.)

## Step 7 — 7-day burn audit
Check the Dune credits dashboard daily. Budget: steady state < 600 credits/mo
(≈ 20/day; expected usage is 1 small execution + KB-scale probe reads per day).
If the pace is over budget, disable the cron first, debug second.

## Monthly — freeze ritual (the 3rd of each month)
```
DUNE_QID_X402_CUMULATIVE=<id> DUNE_QID_REGISTRY=<id> \
node scripts/dune/freeze-month.mjs
git add scripts/dune/baselines.json && git commit && git push
```
Folds the closed month into the frozen baseline and advances `{{window_start}}`
(via baselines.json — the pipeline passes it as a query parameter; NEVER PATCH
the SQL). Refuses to fold if the latest stored result predates the new cutoff;
`--execute` spends one execution to fix that. Automate later if it proves
boring.

## §registry-fallback (if the registry window can't fit 2 min)
In order of preference:
1. Shorten the window: run freeze-month.mjs early (any 1st-of-month cutoff is
   valid) so the scan span shrinks.
2. Split the query: evms.logs and sepolia.logs as two separate Dune queries,
   two cheap executions.
3. Park it: leave `DUNE_QID_REGISTRY` unset — the pipeline keeps publishing the
   frozen registry section from the previous build with honest asOf stamps and
   an SLA-red flag. The site stays correct, just stale on that one section.
